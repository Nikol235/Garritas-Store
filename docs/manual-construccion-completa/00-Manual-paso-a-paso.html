1. Antes de empezar: qué vas a construir

Vas a reconstruir Garritas Store, una tienda de mascotas con compras, citas, sedes, logística, cuentas y suscripciones. Empezarás con una carpeta vacía. Crearás archivos en rutas exactas y entenderás por qué existen antes de ejecutarlos.

La guía sigue el enfoque del ingeniero Ángel Sullon Macalupu en Pagatu, sesiones 1 a 11: servicio REST, configuración, descubrimiento, Gateway, resiliencia, seguridad, eventos, consistencia, observabilidad y frontend. Se adapta el dominio; no se atribuye a Garritas una copia literal de Pagatu.

Este manual enseña la versión final de cada archivo. Las etapas tempranas todavía no constituyen un sistema completo: algunos módulos necesitan la configuración y las dependencias de etapas posteriores. En cada punto se indica qué puedes comprobar. No se inventa un historial de versiones intermedias.

13. Etapa 6: Kafka y mensajería

Crea kafka/compose-dev.yml y los demás archivos de su etapa. Kafka es un broker de eventos; Kafka UI es su interfaz de inspección. El puerto 19092 es TCP para clientes del host y 18085 corresponde a la página web.

docker compose -f kafka/compose-dev.yml up -d --wait --wait-timeout 240
Start-Process "http://localhost:18085"

Las aplicaciones Java en Windows conectan a localhost:19092. Kafka UI, dentro de Docker, conecta al alias de red del broker: no usa localhost para otro contenedor. Mezclar esas direcciones causa fallos de conexión aunque el contenedor figure iniciado.

El topic de negocio es garritas.ventas.v1. Venta, Catálogo y Pago tienen grupos distintos para que cada servicio reciba los eventos que necesita. El productor usa la venta como clave para mantener el orden de esa clave dentro de una partición. Tres particiones y una réplica son configuración de laboratorio, no alta disponibilidad.

Si Pagatu ocupa 19092 o 18085, primero identifica el contenedor. Detén únicamente el contenedor de Pagatu que ocupa el puerto si no lo están utilizando tus compañeras. No borres volúmenes para resolver una colisión.

15. PostgreSQL y Flyway: crear las bases

Cada dominio trae compose-dev.yml para su PostgreSQL. No crees una única base compartida para los ocho servicios. Flyway aplica las migraciones al iniciar cada aplicación, antes de que JPA valide el esquema.

# Ejemplo: al haber creado la etapa 7.
docker compose -f services/garritas-catalogo-ms/compose-dev.yml up -d

Copia TODAS las migraciones V1, V2, V3… que aparezcan en la etapa, no solo V1. Si una migración ya se aplicó, añadir una nueva V es preferible a modificar la anterior. R__ corresponde a migración repetible; los ejemplos peruanos de db/demo se cargan en DEV.

En application.yml de cada servicio se importa Config. El datasource DEV apunta a localhost:1544x porque Java corre en Windows; el PostgreSQL escucha 5432 dentro de su contenedor. ddl-auto: validate comprueba el modelo, no crea las tablas automáticamente.

No borres volúmenes ni hagas flyway repair como primer intento ante un error. Lee la migración, el checksum y la base concreta. Docker down -v elimina datos persistidos.

services/garritas-catalogo-ms/src/main/java/pe/edu/upeu/garritas/catalogo/service/CategoriaService.java
package pe.edu.upeu.garritas.catalogo.service;

import java.util.List;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import pe.edu.upeu.garritas.catalogo.dto.CategoriaRequest;
import pe.edu.upeu.garritas.catalogo.dto.CategoriaResponse;
import pe.edu.upeu.garritas.catalogo.entity.Categoria;
import pe.edu.upeu.garritas.catalogo.exception.ResourceNotFoundException;
import pe.edu.upeu.garritas.catalogo.mapper.CategoriaMapper;
import pe.edu.upeu.garritas.catalogo.repository.CategoriaRepository;

@org.springframework.transaction.annotation.Transactional
@Service
@RequiredArgsConstructor
public class CategoriaService {

  private final CategoriaRepository categoriaRepository;
  private final CategoriaMapper categoriaMapper;

  public List<CategoriaResponse> listar() {
    return categoriaRepository.findAll().stream().map(categoriaMapper::toResponse).toList();
  }

  public CategoriaResponse obtener(Long id) {
    return categoriaMapper.toResponse(buscarOFallar(id));
  }

  public CategoriaResponse crear(CategoriaRequest request) {
    Categoria categoria = categoriaMapper.toEntity(request);
    return categoriaMapper.toResponse(categoriaRepository.save(categoria));
  }

  public CategoriaResponse actualizar(Long id, CategoriaRequest request) {
    Categoria categoria = buscarOFallar(id);
    categoria.setNombre(request.getNombre());
    categoria.setDescripcion(request.getDescripcion());
    return categoriaMapper.toResponse(categoriaRepository.save(categoria));
  }

  public void eliminar(Long id) {
    categoriaRepository.delete(buscarOFallar(id));
  }

  private Categoria buscarOFallar(Long id) {
    return categoriaRepository
        .findById(id)
        .orElseThrow(() -> new ResourceNotFoundException("Categoria no encontrada: " + id));
  }
}

18. Etapa 9: Usuario, perfil, mascotas y suscripciones

Usuario vincula el sub de Keycloak con el perfil del negocio. No guarda contraseñas de login ni emite JWT. Crea las entidades, DTO, repositorios y servicios de usuarios, mascotas, roles internos, planes, suscripciones y períodos.

  2. Valida DNI de ocho dígitos y teléfono peruano, cuando se proporcione, de nueve dígitos empezando por 9. No uses una entrada numérica que elimine ceros o acepte notación científica.

21. Etapa 12: Venta, cabecera y detalles

Venta recibe el checkout y coordina la compra. Crea Venta y DetalleVenta, DTO, repositorios, servicio, clientes remotos, eventos y despacho. Venta → detalles es 1:N; cada detalle guarda producto, cantidad y precio acordado.

  1. CLIENTE envía productos/cantidades, sede, entrega y método. ADMIN no compra, incluso si además tiene CLIENTE.
  2. Venta verifica propietario, clave de idempotencia, sede, productos, stock observado y tarifa vigente. Nunca toma el total del navegador como autoridad.
  3. Calcula subtotal + costo de envío. Persiste venta y detalles y añade venta.creada al Outbox en una transacción local.
  4. Responde con la venta pendiente. No afirma que está pagada antes del evento de confirmación.
  5. Los consumidores avanzan la Saga; Angular consulta pedidos hasta conocer el resultado.

La clave Idempotency-Key permite repetir un checkout sin crear dos ventas por la misma operación. Un bloqueo o restricción evita carreras: no es suficiente hacer un SELECT y luego un INSERT sin control concurrente.

Outbox guarda el evento en la misma transacción que el cambio local. Otro proceso lo publica y registra su envío tras confirmación. Un fallo entre publicar y registrar puede repetir el evento: por eso la garantía es al menos una vez, no exactamente una vez en todo el sistema.

Inbox detecta eventId ya consumidos dentro de la transacción del consumidor. Además se necesitan reglas de negocio por idVenta: un duplicado semántico con otro eventId tampoco debe reservar o crear despacho otra vez. Las restricciones y estados de la reserva cubren ese caso.

33. Prueba funcional guiada: del maestro a la compra

  1. ADMIN: inicia sesión con admin-store. Comprueba que puedes administrar sedes, productos, servicios y coberturas; que no aparece un carrito de compra operativo para ADMIN.
  2. ADMIN: deja un producto activo con stock y categorías. Configura una sede activa y una cobertura con una tarifa conocida.
  3. CLIENTE: entra como cliente. Guarda perfil y vuelve a cargarlo; crea mascota con edad y unidad explícita.
  4. CLIENTE: añade un producto al carrito. Selecciona sede y delivery; verifica subtotal + tarifa = total. Usa un método aprobado por la simulación.
  5. Confirma una sola vez. Observa el pedido pendiente y espera PAGADA. Comprueba que existe un despacho, que el total incluye envío y que el stock disminuyó.
  6. ADMIN: consulta y avanza el despacho mediante las transiciones permitidas. No crees un despacho sin una venta elegible.
  7. CLIENTE: reserva una cita con un paquete de la sede; comprueba importe y duración. Intenta un solapamiento para ver el rechazo.
  8. CLIENTE: contrata y renueva un plan. Verifica un período nuevo y su vigencia; cancela e intenta renovar para comprobar la restricción.

Anota los IDs reales de venta, producto, cita y suscripción. Las bases pueden contener ejemplos distintos si ya se usaron; no supongas que todo tiene id 1.
